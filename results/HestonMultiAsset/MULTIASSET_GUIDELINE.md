# Multi-Asset Heston, How to Add a New Method

**Scope.** This file is a **delta** on the repository-root [`GUIDELINE.md`](../../GUIDELINE.md),
not a replacement for it. The root guideline targets the d = 1 benchmark, whose artefacts are
split across `methods/<Method>/` and `results/Heston/<Method>/`, whose paths are `(8192, 128)`,
and whose README carries a Path Shadowing MC section. **None of those three things hold here.**

Where this file is silent, the root guideline applies. Where the two disagree, **this file wins
for anything under `results/HestonMultiAsset/`**.

[`oldreadme.md`](oldreadme.md) in this directory carries a five-step summary of the same process. That
file is **generated** by `tools/render_dataset_readme.py` and is deliberately kept short; this
file is the full specification. If the two ever disagree, this one is authoritative and the
generator's summary should be corrected.

The reference implementation is [`SBTS/`](SBTS/README.md). Copy its structure exactly. SBTS is
non-parametric, so it has **no weights and no training loss**; every other method on this
dataset is a neural network and **must** fill the two slots SBTS leaves empty. Those two
additions are the only intended differences, and §3 and §8.6 below specify them.

## 0. Before you start

Answer these four questions in writing, in `code/README.md`, before touching anything else.

1. **Does the method natively accept `(N, T, d)` input?** If yes, train one model on all 8
   channels. If it is hard-wired to univariate sequences, you train **8 independent models, one
   per asset**, and you say so in the README header — a per-asset ensemble is a different model
   from a joint one and must not be presented as multi-asset.
2. **Does any hyperparameter fail to cross dimension?** SBTS's bandwidth `h` did: its kernel is
   radial, so its support radius has to scale with the typical distance between d-dimensional
   increments, which grows like √d (median pairwise distance 0.0372 at d = 1 vs **0.2643 at
   d = 8**). If you re-select a hyperparameter, re-select it **on the validation split**
   (`heston_ma_S_val_8192x252x8.npy`), never on test, and record the sweep.
3. **What is the memorisation risk?** Any method that can copy training increments must ship the
   NN-ratio diagnostic (§9). This is not optional.
4. **Compute budget.** 5 seeds × 8 192 paths × 252 steps × 8 assets, plus ~11 min per seed of
   metrics. Estimate it before you launch, not after.

## 2. Dataset contract

Ten arrays in `dataset/HestonMultiAsset/`, each `(8192, 252, 8)` float64, prices starting at
`S0 = 100.0` exactly, `dt = 1/252`:

| File | Role |
|------|------|
| `heston_ma_S_8192x252x8.npy` | **train** — the only split a generator may see |
| `heston_ma_S_val_8192x252x8.npy` | **validation** — hyperparameter selection only |
| `heston_ma_S_test_8192x252x8.npy` | **test** — every reported metric is scored against this |
| `heston_ma_S_disc_8192x252x8.npy` | judge split for A18/A19 |
| `heston_ma_S_valdisc_8192x252x8.npy` | validation judge split |
| `heston_ma_v_*.npy` | matching latent variance paths (A33/A34 only) |

The law is `parameters.json`: Szimayer, Dimitroff & Lorenz (2011) parsimonious multi-asset
Heston — 8 independent 1-D Heston marginals coupled **only** through the d(d−1)/2 spot
correlations Σˢ, which makes the correlation of (W, W̃) block diagonal `diag(Σˢ, I_d)` and hence
PSD by construction. Parameters from Ait-Sahalia & Kimmel (2007) JFE 83(2) Table 6, daily SPX.

Per-asset digest **`231da80bdedf22e9`**. If your run prints a different digest, the dataset was
regenerated under a different numpy and **nothing you compute is comparable to SBTS**. Stop and
investigate — `np.random.Generator` is not version-stable across numpy releases.

**Training on anything but the train split is fabrication.** Validation is for hyperparameters.
Test is never seen until `compute_all_multiasset.py` runs.

## 3. Training the 5 seeds — the part SBTS skips

### 3.1 Hardware (hard limits, always enforced)

Max **2 GPUs**, max **16 cores**, ~250 GiB RAM. Run `nvidia-smi` and `htop` **first**: the
machine is shared, and a card that looks free at 19:00 can be at 98 % util by 21:00. Pick the
two idle cards; do not assume 0 and 3.

```bash
# two seeds at a time, one per GPU, 8 cores each
for i in 0 1; do
  CUDA_VISIBLE_DEVICES=$i taskset -c $((i*8))-$((i*8+7)) OMP_NUM_THREADS=8 \
    python code/train_multiasset.py --seed $i &
done
wait
```

Anything running more than ~20 minutes must be detached with `setsid ... & disown`. Do not use
the harness background runner for multi-hour chains — it reaps them.

### 3.2 What each seed must save

**Weights**, `weights/seed_{i}_model.pt`

```python
torch.save(model.state_dict(), f"weights/seed_{i}_model.pt")
```

Non-PyTorch equivalents: `.npz` for numpy, `.pkl` for sklearn. If the method genuinely has no
parameters, ship `weights/README.md` explaining why — as SBTS does, where the "model" *is* the
training array plus `(h, K, N_pi)`. An unexplained empty directory is not acceptable.

**Config**, `weights/seed_{i}_config.json`

```json
{
  "method": "<Method>",
  "seed": 0,
  "dataset": "HestonMultiAsset",
  "d": 8,
  "seq_len": 252,
  "n_train": 8192,
  "joint_or_per_asset": "joint",
  "hidden_dim": 64,
  "num_layers": 2,
  "batch_size": 128,
  "n_steps": 20000,
  "lr": 0.001,
  "paper_hyperparams": true,
  "retuned_for_d8": [],
  "train_time_sec": 1823.4,
  "gpu": "A100-SXM4-80GB"
}
```

`"joint_or_per_asset"` must be `"joint"` or `"per_asset"` — see §0, question 1.
`"retuned_for_d8"` lists every hyperparameter you changed from the paper's value. An empty list
is a **claim that you changed nothing**, so do not leave it empty by default.

**Losses**, `losses/seed_{i}_losses.csv`, logged every **100 steps**:

```
step,phase,loss_total
100,train,2.481930
200,train,1.902114
```

Add method-specific columns freely (TimeGAN adds `e_loss,s_loss,g_loss,d_loss`); the three above
are the minimum and their names are fixed.

**Loss convergence figure**, `plots/loss_convergence.png`: all 5 seeds overlaid, one subplot per
loss component, 1600×900 at 150 dpi, x-axis = step (not wall time), legend `Seed 0 … Seed 4`.

### 5.1 Per-asset vs native scoping — the rule that defines this dataset

| Scope | Metrics | How |
|-------|---------|-----|
| **native d = 8** | **A6-A11, A18, A20, A25** | evaluated **once** on the full `(N, T, 8)` tensor |
| **per-asset mean** | everything else | computed on each of the 8 univariate slices, reported as the **mean over assets** |

Native rows carry the literal tag `*(native d=8)*` in the README tables — 10 rows, no more. The
per-asset breakdown goes to `metrics_per_asset.csv` (8 rows per metric).

Do not extend the native set without changing `NATIVE_LABEL` in
`tools/render_dataset_readme.py` in the same commit, or the dataset page will describe a set
that no longer matches the method pages.

**A19 is deliberately per-asset even though a native call would execute without error.**
`metrics/predictive_score.py::_train_gru` targets `data_t[idx, 1:, :1]` — only the *first*
feature. A native d = 8 run therefore returns an asset-0-only number under a multi-asset name.
Leave it per-asset.

**A20 is the row that matters most here.** It is the error on the full terminal covariance
matrix, i.e. the only metric that actually tests whether the d(d−1)/2 spot correlations Σˢ
survived generation. A method can look excellent on every marginal metric and still destroy the
dependence structure. Lead with A20 when you summarise a multi-asset result.

## 6. The perfect-recovery floor — already computed, shared, do not regenerate

`perfect_recovery/` holds five **fresh independent draws** from the same SDE with the same
frozen per-asset parameters at seeds 1000-1004, scored with byte-identical metric code
(root GUIDELINE §5.4). It is **non-zero everywhere** and **shared by every method** on this
dataset. Its metrics are computed once; reuse them.

Two things to internalise:

- It is **not** a permutation of the test set. A permutation preserves every column-wise
  statistic exactly, collapses most metrics to 0, and is a misleading target.
- **Beating the floor is a red flag, not a win.** The floor *is* the data-generating process;
  nothing can legitimately outperform it. A method landing materially below it on a
  distributional metric is almost certainly reusing training data — a generator that resamples
  training increments inherits less sampling noise than an independent draw, which shows up as
  a *lower* Wasserstein distance. Check §9 before writing a word of celebration into the README.

If you ever must rebuild it:

```bash
/home/tbasseras/sbts-venv/bin/python metrics/gen_perfect_recovery_multiasset.py
```

The script guards on the per-asset digest. **If the guard fires, do not bypass it.**


Three rules that are easy to get wrong:

- **`seq\_len` must be escaped.** A bare `seq_len` in prose starts a markdown italic run that
  swallows text until the next underscore. Same for any `A18_disc_score_gru` written outside a
  code span.
- **Every hyperparameter is attributed to paper-or-you.** "We used h=0.31" is not attribution.
  "`K` and `N_pi` are the author's values, confirmed 2026-07-27 for the d = 1 benchmark; **`h`
  is ours**" is.
- **A re-tuned hyperparameter must carry the quantified failure it avoids.** Not "the paper's
  value works badly at d = 8" — that is unfalsifiable. SBTS writes: *40.8 % volatility error,
  excess kurtosis 45.66 against a real 1.12, minimum price 0.0.* Three measured numbers, each
  reproducible from the recorded sweep. If you cannot produce them, you did not do the sweep.

If you re-tuned **nothing**, say so explicitly and name the hyperparameters you checked. Silence
reads as "did not look".

### 8.3 Number formatting — one function, applied everywhere

All numeric cells go through a single `fmt()`. Reproduce it exactly; a renderer that formats
the A table one way and the B table another produces a page that cannot be compared with itself.

| Input | Rendered | Rule |
|---|---|---|
| `None` or `""` | `-` | missing, not zero |
| `NaN` | `nan` | never silently blanked |
| `0.0` | `0` | exact zero, no decimals |
| `4.58e-05` | `4.58e-05` | `abs(v) < 1e-3` → `f"{v:.2e}"` |
| `0.01811` | `0.01811` | otherwise 4 significant digits |
| `1.0` | `1` | trailing zeros stripped |

Mean cells are `f"{fmt(mean)} ± {fmt(std)}"` — one space either side of `±`, the literal U+00B1
character, never `+/-`.

Percentage rows carry `%` **inside every cell** (`3.317% ± 0.05786%`), not once in the column
header. The B table mixes percent rows and bare-ratio rows in the same column, so a header-level
unit would be wrong on half the rows.

`nan` in a shipped table is a defect, not a formatting outcome. Trace it before you publish.

### 8.4 Section 3 — the A table

**Header, exactly 9 columns:**

```
| Metric | Mean ± Std | Seed 0 | Seed 1 | Seed 2 | Seed 3 | Seed 4 | Perfect floor |
```

Build the seed columns from `len(seeds)`, never a hard-coded `range(5)`. A run that lost a seed
must render 8 columns and be obviously wrong, not silently render an empty 9th.

**Preceded by a scoping blockquote** naming the log-return convention, the A26 exception
(price increments `ΔS_t`), and what `*(native d=8)*` means, with a link to
`metrics_per_asset.csv`.

**Category separator rows** partition the metrics: Fat Tail, Distribution, Temporal,
Volatility, Heston Spec. They span the full width with empty cells:
`| **, Fat Tail, ** | | | | | | | |`. See §8.10 before you "fix" that comma.

**Direction arrows** suffix the metric label: ` ↓` lower-is-better, ` ↑` higher-is-better, and
the empty string for a metric with no monotone direction (A28, whose target is 1.0, rendered
`A28 Kurtosis Ratio (→ 1)`).

**The native tag** ` *(native d=8)*` follows the arrow, on **exactly these 10 rows and no
others**:

```
A6_path_mmd2   A7_terminal_mmd2   A8_increment_mmd2   A9_volatility_mmd
A10_terminal_swd   A11_path_swd   A18_disc_score_gru   A18_disc_score_mlp
A20_cov_error   A25_mean_rmse
```

Everything else is computed on each of the 8 univariate slices and averaged. **A19 is
deliberately not native** — `predictive_score.py::_train_gru` targets `data_t[idx, 1:, :1]`,
i.e. the first feature only, so a native run reports an asset-0 number under a multi-asset name.
If you tag A19, you have shipped a mislabelled metric.

**Three trailing blockquotes, in this order:**

1. **Convention** — arrow legend, plus A28's perfect value.
2. **Headline** — `**N of the M A-metric rows sit at or below the independent-draw floor**`
   followed by the row names, then the largest remaining gaps as
   `**<name>** (<value> vs floor <floor>, <ratio>×)`. Every one of those numbers is computed,
   never typed. `M` is the number of *displayed* rows, not 34: several A-keys expand into two
   rows (GRU/MLP) and the count must match what the reader can see.
3. **Perfect floor** — what it is (§6), and explicitly what it is **not** (a permutation of the
   test set).

Then a short glossary walking A1-A5, A6-A11, A12-A17, A18, A19, A20, A21-A24, A25, A26-A32,
A33-A34, saying for each block what it measures and — for the native ones — why a multivariate
generalisation is meaningful there and nowhere else.

### 8.5 Section 4 — the B table

**Header, exactly 10 columns** — the A header plus `Measure` in position 2:

```
| Plot | Measure | Mean ± Std | Seed 0 | Seed 1 | Seed 2 | Seed 3 | Seed 4 | Perfect floor |
```

**Preceded by prose** defining the three sub-scores (curve `L`, first difference `L'`, second
difference `L''`), stating that the curve is computed **per asset and averaged over the 8 assets
before** the combination so the combination rules stay byte-identical to the d = 1 tree, and
justifying why `% err`, `NRMSE` and both CVaR rows are **funct-only** (the derivative curves have
near-zero true values, so relative error explodes into meaningless 10⁴-% figures).

**Row structure:**

- First data row is `grid_tvd` — one row, not five, measure label `grid_tvd 50×50 (%)`, plot
  label `**Path comparison** *(50×50 path-cloud)*`.
- Then **6 plots × 5 sublines** = 30 rows. Subline order is fixed:
  `MSE`, `% err`, `NRMSE`, `CVaR₉₀`, `CVaR₉₅`.
- The **Plot cell is bold on subline 1 and empty on sublines 2-5** — `|  | % err | …`. Two
  spaces, not a repeated label. Repeating it makes the grouping unreadable.
- Plot order: Log-return histogram, QQ plot, ACF \|r\|, ACF r², Rolling vol histogram,
  Tail survival.

**`ACF |r|` must be written `ACF \|r\|`.** An unescaped pipe splits the row into extra columns
and produces a ragged table that *still renders*, so the eye does not catch it. This is check 2
of §8.9 and it exists because the failure is invisible.

**Two trailing blockquotes:** the headline (`**N of the 6 B plots** sit at or below the
finite-sample floor on the deciding MSE row`, with the names or the literal `none`), and a
cross-seed stability note. Deterministic methods should say why their seed spread is small;
GAN-family methods must state whether any seed collapsed.

## 9. Memorisation diagnostic — required, not optional

```bash
/home/tbasseras/gpu-venv/bin/python \
    results/HestonMultiAsset/<Method>/code/measure_memorisation.py --seeds 0,1,2,3,4
```

Writes `losses/memorisation.json`:

```json
{ "nn_ratio": 0.215, "nn_ratio_std": 0.0043, "n_exact_duplicates": 0 }
```

`nn_ratio = median NN(generated → train) / median NN(held-out → train)` in log-return space,
flattened to `(T − 1)·d = 2008` dimensions.

Calibration: **independent draws score 1.0001.** A ratio well below 1 means generated paths sit
closer to the training set than genuine held-out data does — that is memorisation. SBTS scores
**0.215**, i.e. ~4.6× closer.

Report the number in the dataset README whatever it says. A low ratio is a **finding**, not a
failure to hide, and it is the correct explanation for any metric that appears to beat the floor.
