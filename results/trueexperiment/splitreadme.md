# Split-half robustness of tables A and B

Generated by `render_splitreadme.py`. Every number below is computed from artefacts on disk; none is typed in. The adjudication rule is imported from `render_comparison.py`, so it is the same code that rendered the published tables -- only the evaluation data changes.

## What was run and why

The published tables score every generator on all 6 144 test windows and report `+/-` as the spread **across seeds**. That quantifies generator randomness. It does not quantify what happens if the test era had been cut somewhere else, and nothing in the published tables does.

So the test era was cut in half and each half scored independently:

| Panel | Real evaluation windows | Generator bank |
|---|---|---|
| `half A` | test/disc `[0:3072]` | first 3 072 paths |
| `half B` | test/disc `[3072:6144]` | first 3 072 paths (identical) |

The bank is held **fixed and identical** across the two halves. That is the whole point of the design: any movement between the A and B columns is split sensitivity, because the generators drew the same paths in both. `disc` was halved as well as `test`, otherwise the adversarial and predictive rows (A18/A19, which score against `disc`) would not have been tested at all.

46 seed-evaluations in total: 5 seeds x 4 generators x 2 halves, plus the 3-seed real-vs-real floor x 2 halves. All 46 completed; none failed.

> **Caveat that applies to both halves equally.** N drops from 6 144 to 3 072, so each half is noisier than the published panel in absolute terms. That is not the comparison being made here. A and B have the *same* N and the *same* bank, so A-vs-B disagreement is attributable to the split alone.

### Can specific events be attached?

**No named event is attached to either half, in this file or anywhere in the repo.** What can be pinned down is which blocks carry the extremes:

* The single most volatile block in the whole era is block 1 (2025-03-05 to 2025-03-16, vol 1.088), in half A.
* Each half contains exactly **one** extreme-kurtosis jump block -- block 9 in A (kurtosis 223) and block 15 in B (kurtosis 211). They largely cancel, which is why pooled kurtosis is so similar across the two halves (46.4 vs 44.4) despite the vol gap.
* Named-event attribution is **not** offered here. The block dates are verifiable from `true_t0_test_6144.npy`; mapping them onto specific market events is not something this repo can check, and a guessed attribution in a results README is worse than none. The regime statistics above are measured and stand on their own.

## 5. What this means

1. **The Deep-MKV-TS vs `reference` result is verified against the split.** It holds on both halves at essentially the published rate. It is the one claim here backed by evidence rather than a single cut of the data.
2. **The generator leaderboard is not resolved at this sample size.** Deep-MKV-TS, SBTS and CSDI sit close enough together that which one wins a given row is decided by the split. The `reference` column is the control that proves this is not generic harness noise: that comparison has a large margin everywhere and never destabilises.
3. **The `Closer to floor` column is fragile by construction.** It is a hard argmin over methods separated by less than split noise. Reporting a winner there implies a resolution the data does not have. That is a defect of the statistic, not a defect specific to any one method.
4. **Do not read the half-B result as a generalisation finding.** Half B is further from the training regime *and* Deep-MKV-TS does worse on it, which is a tempting story. With two halves it is one observation. It is a hypothesis worth testing, not a result.

## 6. Reproducing

```
python results/trueexperiment/splithalf/prep.py       # build the two halves
bash   results/trueexperiment/splithalf/one_seed.sh <half> <method> <seed> <gpu> <cores>
python results/trueexperiment/splithalf/merge.py      # per-seed JSON -> aggregates
python results/trueexperiment/render_splitreadme.py   # this file
```

`splithalf/` holds the aggregate CSV/JSON artefacts and the per-seed metric JSONs for both halves. Path banks are not stored -- `prep.py` rebuilds them from the published `generated_paths/` trees. `manifest.json` records the provenance of the cut.

Note that `prep.py`, `one_seed.sh` and `merge.py` are the scripts exactly as run, and they read and write under `/tmp/splithalf` (their `OUT` constant). They were kept that way deliberately so the run could not touch `results/` or `dataset/`. The files in `splithalf/` are copies of the aggregates those scripts produced; only `render_splitreadme.py` reads from this directory.
